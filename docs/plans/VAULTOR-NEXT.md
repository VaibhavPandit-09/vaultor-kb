# Vaultor Next migration tracker

Reviewed 2026-11-11. Authoritative experimental replacement tracker. Published Windows/macOS 0.27.0 remain Electron/Java. This milestone does not merge, tag or publish releases; Android is on hold.

## Target and implemented milestones

Tauri 2 + React/TypeScript + Tiptap + Rust + SQLite. Normal local work uses direct commands, with no HTTP server, JVM or permanent helper process. `next/` owns the native application; `frontend/src/next/` is its separate frontend entry point. Original implementations remain intact as reference and benchmark baseline.

M1 completed at `52b84ee`: isolated workspaces, exclusive process ownership, Rust/SQLite persistence, collections, structured Tiptap notes, revision-checked saves, shared panes/history, workspace themes, normal-close save barrier and offline milestone Help.

M2 adds same-database durable drafts, explicit recovery/conflict review, keyset Library pages, nested/renamable collections and atomic identity-based memberships. `editing.rs` and `library.rs` extend the portable domain; the connection still has one storage-thread owner. Schema/marker 2 intentionally refuse M1 data without migration. A new default `Workspace-M2` avoids modifying the M1 default. Previously remembered older paths can be replaced using Open workspace and a new empty folder.

M3 extends this same schema/domain with page-scoped selection, roving row focus, consistent resource/collection/background menus, searchable bulk destinations and one transactional bulk-membership command. No new database, backend process, framework or migration is introduced. M4 adds committed FTS5 search, collection/title/content/order filters, cursor-based result navigation and focused opening-work recovery.

The portable Rust domain has no Tauri types. One storage thread owns SQLite and transactions; async handlers await receipts. No legacy migrations are provided. Nonempty unrelated directories, open workspaces and newer schemas are refused. The default profile has its own application identifier. Explicit benchmark workspace overrides never change the remembered personal workspace.

## Interaction decisions

The old Dashboard combines HTTP lifecycle, source authority and many unfinished capabilities. The new entry composes retained Tiptap packages, CodeBlockView, symbol rules, shared documents/history, Escape ownership, theme reveal and design tokens without mounting that orchestration. M2's document-owned EditingSession replaces M1 SaveCoordinator for this entry only. This is an adapted editor composition, not full BlockEditor parity.

Library/collection selection changes the same resource list. Opening a note retains list context. Opening beside gives the existing editor less space; closing restores its bounds with shared motion timings and immediate reduced-motion endpoints. Library and editor scroll independently as separate working regions; no duplicate/sticky header is introduced. Theme uses the shared reveal controller. Navigation and normal close await saves and retain the editor on failure. Correctness never awaits animation.

## M2 editing and Library contracts

One draft per resource lives in the workspace SQLite database, independently of the committed note. It binds base revision, random editor token and monotonic sequence to the exact title/JSON. Protection is requested after 250 ms quiet or 1 second continuous typing; actual durability begins at the SQLite FULL/WAL receipt, not the timer deadline. Autosave follows 1 second quiet. Full JSON is captured for protection, not every keystroke. Two views share the document and journal owner. There is no idle polling.

Save verifies the exact protected evidence and expected note revision; note commit and matching-draft deletion share one transaction. Stale revisions retain the journal. Recovery compares protected and current text/title on demand, supports explicit restore/discard, and can park a draft without blocking other documents or normal closing. Choosing a draft over a competing saved version conditionally rebases against the reviewed revision; no automatic merge. Conflicting or quota-blocked evidence never silently expires. Limits are 64 drafts / 32 MiB of document bodies and 8 MiB per note. Unsynchronized edits and unreached durability receipts cannot survive power loss. Previews cap display at 200,000 characters without truncating storage.

Library reads at most 100 metadata summaries per request and mounts one page. Immutable descending creation sequence plus an anchor high-water mark excludes later insertions during traversal; note edits do not reorder pages. Cursors carry collection scope. Membership changes are live, not a database snapshot, and the owning UI refreshes page one after organization changes. Previous/Next preserve open editors and per-page scroll. No virtualization dependency is needed for bounded 100-row rendering. Full note bodies load only for editing/recovery, not organization.

Collections have parent IDs and sibling-normalized unique names; reparenting rejects cycles. Add/remove/move update the resource/collection join transactionally; resources can have multiple memberships and retain one ID/body. M3 extends this authority to1–100 unique resources per transaction, validating all resource/collection IDs before writes and rolling back on any error. Receipts report actual added/removed/unchanged counts; repeated membership actions are safe no-ops. Other placements and note revisions/content are untouched.

## M3 interaction contract

Ordinary title activation opens without an explicit multi-selection. Ctrl/checkbox toggles, Shift ranges and Ctrl+Shift additive ranges follow displayed resource IDs. One selection/focus/anchor model is scoped by collection and page cursor; page/scope changes clear it, same-page refresh/rename prune to visible IDs, and successful organization clears it. No unloaded resources are selected. Arrow/Home/End move focus; Enter opens only that focused note; Space toggles and Ctrl+A selects the loaded page. DOM target admission confines these shortcuts to the list, never editor text, fields, menus or dialogs. Editor Escape returns to a visible Library row; menu/modal Escape has higher centralized priority than selection.

Right-clicking a selected row preserves the group; an unselected row becomes the sole selection. One context-menu instance uses existing MenuAction presentation, shared motion classes and Escape/portal focus owners, with viewport clamping, keyboard traversal and invoker restoration. There is no menu/listener per row. Resource, collection and blank-space commands expose implemented actions only. Bulk destinations reuse AppModal and a bounded searchable collection picker. Header metadata/actions compress into selected-count/organization mode without a second toolbar or duplicated header. Collection branches transform their existing grid track with inert collapsed descendants and reduced-motion endpoints. Active editors retain their keys across selection and menu work.

## Boundaries

- M8 adds managed deletion/Trash, tags and pins; external/media search remain future work. Collection contents are direct memberships, not recursive descendant aggregation. Selection is deliberately limited to the current loaded page.
- M5 exposes linked Markdown through registered local NTFS roots. M7 adds managed imports/exports; rich previews, images/attachments and managed resource-link commands remain pending.
- Only acknowledged journal/commit bytes are durable. There is no automatic conflict merge or recovery export, and unresolved evidence requires an explicit decision. This experimental app still needs independent copies of important information.
- Windows only. No installer, signing/updater, macOS, Android or LAN API qualification. Native menus, keyboard customization, slash menus, pane session restoration and full animation parity remain incomplete. Physical IME/accessibility acceptance is unclaimed.

## Build and run

Install stable Rust MSVC, Windows C++ Build Tools/SDK and WebView2. Add the user's `.cargo/bin` to PATH. Run `npm ci --prefix frontend`, `npm ci --prefix next`, then `npm --prefix next run dev` or `npm --prefix next run build`. The optimized build produces `next/src-tauri/target/release/vaultor-next.exe`, without an installer. Do not point it at published data. `VAULTOR_NEXT_WORKSPACE` is a disposable-test override.

## M4 search and performance contracts

FTS5 is available in bundled SQLite. One transactional initialization backfills M2/M3 workspaces from saved JSON text nodes; no Electron/M1 migration is added. SQLite triggers maintain title/plain-text index and a generation in the same save transaction. Drafts never enter the index. Query words are escaped, ANDed prefixes (Unicode case/accent-insensitive), capped at256characters/12words. No raw MATCH language is exposed. Results contain at most100 summaries; documents load only on opening. Creation, recent modification and title ordering use deterministic seq tie-breakers. Search cursors bind the exact options and generation: writes/membership changes invalidate further paging rather than silently skipping/repeating rows. Refresh starts a fresh page.

The Library search field stays in its compact list region and shares the existing LibraryPopover, tokens, menus and Escape/focus ownership. Query execution waits220ms; stale epochs cannot publish over newer queries/scopes. Only delayed activity exposes a progress underline; editor state and list geometry stay mounted. Down enters results; list Enter opens, field Ctrl+A edits text, list Escape clears selection before filters, editor Escape returns to its row. Clear restores the previous browse page in the same collection. No Saved Searches/history system or retained result cache is introduced; scroll offsets are bounded to64entries.

A retained production M3 EXE reproduced opening latency around57ms and4243 Library DOM mutations across three opens. Independent64KiB read roundtrips were2.7–4.2ms (IPC/SQL/serialization together, not isolated SQL). The matching diagnostic M4 build reduced those mutations to70 and median opening57.0→28.8ms over3 opens, with read roundtrips still2.7–3.8ms. Stable event callbacks and removal of row-wide busy props eliminate avoidable list updates; guards still refuse actions during operations. React/Tiptap/layout costs are not individually instrumented, and animations are preserved. There is no new idle timer or database polling; debounce/loading timers exist only for pending requests. Final before/after measurements and limitations belong to the canonical benchmark records.

## M5 linked-source contracts

`linked/` owns parsing/verified source-range patches, the Windows handle-bound filesystem adapter, and same-database source/document/draft/Save-intent coordination. React owns one session per logical document using retained Tiptap/history/panes. JSON is captured for debounced protection; there is no external autosave, recursive startup scan, idle polling or retained clean-file cache. Physical replacements acquire different identities; pending Save intents retain the original recovery identity.

Root and parent handles are pinned without delete sharing. Revision checks use physical identity plus SHA-256, never timestamps alone. Reads cap at1MiB; rich editing at256KiB,64 nesting levels/2000 top-level blocks. Directories return100entries while examining at most20,000 per request. The supported syntax and recovery choices are in [experimental Help](../help/next-foundation.md). The complete patched candidate must reparse to the proposed structured document before publication.

Drafts carry hash-verified baseline bytes, editor JSON and token/sequence in SQLite (64documents/32MiB). Explicit Save freezes the proof, checks source identity/hash under a lease, journals intent, stages/flushes a same-directory candidate, captures the original and publishes through a non-replacing handle-relative rename. Owner/group/DACL/inheritance, creation time and ordinary attributes are checked; candidate content/metadata are verified before cleanup. The original inode is never rewritten. Unsupported filesystem metadata is refused; optional audit metadata and concurrent security administration are not qualified.

No atomic-CAS guarantee is claimed. A gap occupant is untouched; failed/uncertain publication keeps original/candidate evidence and protected content. Startup never replays writes. Explicit outcome verification accepts only an exact original or candidate identity/hash; other cases require manual attention. Unsupported visual edits remain journaled even when Save refuses them. Registration removal only deactivates authority and keeps recovery. Managed FTS/collection membership does not include linked files. Native acceptance and benchmark outcomes follow below.

## M7 transfers and Activity contract

`activity.rs` owns an eight-queued-job, one-at-a-time on-demand worker, real item/byte progress (coalesced to100ms), cancellation checks during64KiB stream chunks, final non-cancellable publication, and64 task summaries retained for30days. No idle polling thread exists. The profile history JSON is atomically replaced and exclusively owned; interrupted tasks become Interrupted and never auto-replay. Event listeners are reference-counted; only Activity/transfer controls observe progress, not the main editor/list. Storage requests remain on the existing actor, bind their expected workspace root and use short transactions. Active/queued tasks prevent workspace switching.

Managed originals are immutable UUID blobs indexed by `managed_originals` (resource ID, initial filename, SHA-256, byte count, kind and relative provenance). Discovery rejects source links/reparse points, workspace overlap, over20,000entries/32levels,1GiB files or10GiB totals. Source bytes stream outside the actor and must match the reviewed hash before publication/metadata commit. Each file commits independently; directory collections reuse normalized sibling names. Filename/hash duplicates skip globally by default without adding a new membership; separate copies require review opt-in. UTF-8 text/supported Markdown <=256KiB become notes; all other bytes remain managed originals. Errors/cancellation can leave committed resources and collections; summaries describe that partial model. Normal failure/cancellation drops owned staging. Forced termination can leave unreferenced blobs or uniquely named output stages; there is no automatic destructive orphan scavenger.

Portable format v1 uses8byte ASCII `VAULTOR1`, little-endian u64 manifest byte length,32byte SHA-256 of the manifest, UTF-8 JSON manifest, then original payloads in inventory order. There are no archive entry paths to extract. UUID inventory, names, hierarchy/cycles, memberships, version, settings, length/count bounds, manifest digest, every original digest and exact EOF are validated. JSON is limited to32MiB/20,000resources; payload limits match import. The single-owner snapshot captures committed notes/revisions/order/timestamps, collections, memberships, originals and supported settings; immutable blobs make later streaming consistent. Protected drafts/linked publication evidence block export. Linked registrations/contents, Activity history and machine connections are excluded; restoration grants no external authority.

Resource exports stage a new directory; archives stage a new file. Outputs never overwrite destinations. Archive publication uses a no-replace hard link (same-volume staging); Windows directory publication uses non-replacing MoveFileW. Restore verifies in a new staged workspace, commits SQLite, runs integrity/checkpoint verification, drops its lock and publishes a new directory. It never overwrites an existing workspace. Source selection/hash/streaming and JSON parsing remain off the storage actor; snapshot construction is bounded. Existing-workspace merge is explicitly M10. Full media previews/native Activity projection remain later work.
