# Vaultor 0.22.0 — recursive collection deletion

Source: immutable `v0.22.0` / `55c1f1b47add18bed785dc6f3b960705621cc6eb`. Based on clean complete-platform0.21.0 master. API protocol3, structured notes, resource identity and archive formats remain compatible. Desktop package/lock both0.22.0; Android is unchanged.

## Behavior

- Delete any supported collection subtree through one shared confirmation. Database counts include the root, distinct managed originals, outside memberships and linked references. Keep resources is selected initially.
- Explicit Trash moves only active exclusive managed notes/files; shared originals retain their outside memberships. Linked references lose memberships only. No physical linked file/source/recovery cleanup or permanent purge occurs.
- Existing save-or-durable-recovery protection runs before Trash; only actually trashed sessions close. Keep preserves mounted editors. Ordinary resource Restore retains IDs/content/tags/pins but cannot restore deleted collection organization.
- A generation-bound plan, current resource revisions, existing Trash lifecycle, child-first collection/membership removal and durable receipt commit in one transaction. Stale plans/revisions reject the whole mutation. Identical operation retries replay the receipt; uncertain responses never silently create another request.
- Batched local session reconciliation precedes navigation to the surviving parent or Collections. Pending purge cleanup/unknown resource kinds refuse safely. Collection-level Trash/restoration is outside scope.
